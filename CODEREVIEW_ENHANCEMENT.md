## P1 — High

### [R-003] Bound aggregate collection and missing-snapshot memory

- **Type:** Review finding
- **Priority rationale:** An upstream response shape admitted by the current limits can exhaust the service process and stop polling, delivery, and the authenticated UI. This is a high-impact availability risk, but it depends on unusually large provider data rather than being an unconditional failure.
- **Location:** `internal/tailscale/client.go:448-506`, `internal/tailscale/client.go:578-585`, `internal/tailscale/client.go:216-228`, `internal/store/snapshots.go:168-202`, and `compose.yaml:7-10`.
- **Evidence:** PR #100 added collector-specific item/byte ceilings, bounded page and device-detail workers, and an aggregate guard that aborts before an oversized result is appended. Snapshot reconciliation now performs a bounded missing-resource scan before loading raw values, so mass-removal protection does not materialize the entire missing set.
- **Impact:** A large tailnet or unexpectedly verbose provider response now produces a deterministic collector error while preserving the previous snapshot set; allocations and worker concurrency remain bounded by configured limits.
- **Recommendation:** Implemented in PR #100. Keep the documented defaults aligned with the supported tailnet size and review telemetry when operating at the upper boundary.
- **Acceptance / validation:**
  1. Mocked pagination with many near-limit pages fails deterministically at the configured aggregate budget, with no partial snapshot apply and bounded allocation.
  2. A large missing-resource fixture preserves all prior snapshots, reports the guard reason, and does not allocate one raw value per missing row.
  3. Device-detail collection remains bounded under the same item limit and preserves partial-result semantics.
  4. Defaults and operator-configured limits are documented against the supported tailnet size and the 512 MiB Compose profile; metrics expose budget rejection without provider payloads.
- **Effort:** L
- **Confidence:** High
- **Trade-off / challenge:** Lower caps can turn a valid large inventory into a degraded result. The defaults and operator-visible remediation path are documented; review them if the supported tailnet size changes.

### [R-004] Keep signed ledger reconstruction inside the history budget

- **Type:** Review finding
- **Priority rationale:** An authenticated request can cause substantially more data to be loaded than the documented 2 MiB history or 5 MiB evidence budget. This is a high-impact availability and operability gap at large batch sizes, though it requires a large historical batch.
- **Location:** `internal/store/history.go:122-157`, `internal/store/history.go:185-193`, `internal/store/signing.go:377-435`, and `internal/store/evidence.go:156-167`.
- **Evidence:** PR #100 removed full ledger-payload reconstruction from normal history pages. Evidence export uses a separate path that estimates the complete signed payload before loading it and rejects an export that would exceed the configured evidence/history budget.
- **Impact:** Filtered history requests no longer pull every sibling event solely to render ledger metadata, and oversized exports fail deterministically before unbounded payload allocation.
- **Recommendation:** Implemented in PR #100. Keep export-limit regression tests in place when changing the evidence format.
- **Acceptance / validation:**
  1. A fixture with one matching event and many large sibling events keeps `ListHistory` below its byte budget and does not load a complete ledger payload.
  2. An oversized signed batch is rejected before full payload allocation, with a stable error and cursor/remediation information.
  3. A bounded export still verifies its content hash, signature, and ledger links offline.
  4. Tests assert that `BytesRead` reflects all material loaded, including ledger data, and never understates the configured budget.
- **Effort:** M
- **Confidence:** High
- **Trade-off / challenge:** Omitting ledger payloads from the HTML page simplifies the memory contract and moves full verification detail to the bounded evidence-download path. The export path retains signature and ledger verification.

### [R-005] Chunk historical backfills instead of blocking startup on all rows

- **Type:** Review finding
- **Priority rationale:** A schema upgrade can leave a large installation unable to start, even though the runtime now bounds newly written values. This is a high-impact upgrade/recovery risk conditional on accumulated history or a long-lived pre-v12 database.
- **Location:** `internal/store/migrations.go:662-777`, `internal/store/signing.go:250-295`, `internal/store/signing.go:377-435`, and `internal/store/store.go:239-253`/`293-301`.
- **Evidence:** PR #101 converted v11-to-v12 snapshot/event metadata backfills to keyset/cursor batches of 64 rows with durable progress, and converted startup evidence-ledger backfill to bounded transactions with a restart-safe cursor. Completed chunks commit independently and ledger inserts remain idempotent and ordered.
- **Impact:** Upgrade memory and writer hold time are bounded by chunk size. An interruption retries only the incomplete chunk and cannot duplicate signed entries or skip eligible rows.
- **Recommendation:** Implemented in PR #101. Continue using the migration progress logs and verified backups for very large upgrades.
- **Acceptance / validation:**
  1. A fixture containing a large number of historical snapshots/events completes each migration chunk within a fixed memory ceiling and writer-time budget.
  2. Killing the process between chunks and restarting resumes without duplicate ledger entries, skipped rows, or a broken hash chain.
  3. The service exposes clear migration-in-progress/failure status and does not advertise readiness until the required schema work is complete.
  4. A failed chunk rolls back atomically, while completed chunks remain verifiably correct and the next run can continue.
- **Effort:** L
- **Confidence:** High
- **Trade-off / challenge:** The migration remains synchronous for schema compatibility, but each transaction is bounded and resumable. Validate startup duration against the largest supported database during operations testing.

## P2 — Medium

### [E-004] Make the database storage budget real and operator-configurable

- **Type:** Enhancement
- **Priority rationale:** The service already exposes storage pressure and diagnostics, but the advertised database budget does not control writes and cannot be selected by an operator. This can produce misleading remediation and eventual disk exhaustion in long-lived deployments.
- **Location:** `internal/store/storage_limits.go:27-202`, `internal/store/store.go:270-272`, `internal/diagnostics/diagnostics.go:168-177`, `internal/store/status.go:353-373`, `README.md:307-309`/`379-399`, and `compose.yaml:7-10`.
- **Evidence:** PR #101 made storage profiles configurable through standalone and Compose environment variables, persisted the active profile in SQLite metadata, and applies a SQLite logical page ceiling before schema/migration writes. Diagnostics and metrics expose the active limit and pressure, while the append-only evidence ledger is never silently deleted.
- **Impact:** Operators can select a profile that survives restart, and writes fail atomically when the logical database budget is reached instead of allowing an advertised limit to remain advisory.
- **Recommendation:** Implemented in PR #101. Monitor pressure and plan retention/export capacity because signed audit data remains retained by design.
- **Acceptance / validation:**
  1. A configured storage profile survives restart and is visible in settings, `doctor -json`, and metrics.
  2. Tests cover threshold behavior (controlled rejection/pause or an explicitly advisory path) and the exact diagnostic wording.
  3. Ledger growth and cleanup behavior are measurable and documented, including what data remains after the 30-day event sweep.
  4. A full or read-only data directory fails safely without corrupting the evidence chain or losing unrelated settings.
- **Effort:** M–L
- **Confidence:** High
- **Trade-off / challenge:** The hard cap applies to SQLite writes while the append-only ledger is retained. Operators must size the profile and plan export/retention capacity rather than relying on silent audit-data deletion.

### [R-006] Bound evidence verifier input

- **Type:** Review finding
- **Priority rationale:** The verifier is a local administrative command rather than a remote endpoint, so it is not a P1 service exposure. It still accepts unbounded input and can be used accidentally or by automation to consume arbitrary memory; the fix is small and should be scheduled.
- **Location:** `cmd/tailstate/main.go:296-318` and `internal/store/evidence.go:236-249`.
- **Evidence:** PR #100 caps evidence-pack and public-key input before decoding, for both stdin and file paths, and returns a stable over-limit error. Export limits and verifier limits now share the same documented boundary.
- **Impact:** A malformed or unexpectedly large local input cannot force unbounded verifier allocation, while valid exported packs continue to verify.
- **Recommendation:** Implemented in PR #100. Keep the verifier ceiling synchronized with future evidence format versions.
- **Acceptance / validation:**
  1. Oversized stdin and file inputs are rejected before unbounded allocation and return a stable remediation message.
  2. Public-key parsing rejects oversized files without reading them into an unrestricted slice.
  3. Valid 5 MiB-or-smaller exports continue to verify from both stdin and a file.
  4. Tests cover malformed, trailing, and over-limit JSON without panics or excessive memory.
- **Effort:** S
- **Confidence:** High
- **Trade-off / challenge:** The verifier ceiling must stay aligned with the export limit. If future evidence formats legitimately grow, version the limit rather than silently widening the local attack surface.

## Deliberate non-findings and assumptions

- The strict collection decoder intentionally rejects absent, null, or wrongly typed `userInvites` and `webhooks` arrays. The code and tests treat an explicit `[]` as the healthy empty response and use the failure to avoid mass-removal side effects; no provider-schema change is proposed without an exact upstream fixture.
- Shoutrrr accepts every scheme registered by the pinned module. Restricting schemes or hosts would change the documented feature contract and should be a separate egress/threat-model decision.
- The mass-removal guard, two-poll removal confirmation, outbox fencing, proxy-independent credential challenges, CI invariant manifest, and Go toolchain alignment were rechecked as resolved work rather than duplicated findings.
- Dynamic provider keys in policy/DNS payloads are deliberately preserved for drift visibility. Redaction rules and the signed evidence model should be revisited only with a concrete provider fixture showing secret exposure.
